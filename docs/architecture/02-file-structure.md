# AskAU — Repository & File Structure (Phase 1)

Two independent repositories:

| Repository | Contents | Language |
|---|---|---|
| **`api`** | RAG pipeline, retrieval, ingestion, API | Python 3.12 |
| **`web`** | Chat interface and administration console | TypeScript / Next.js |

**Out of scope for both:** container definitions, orchestration manifests, and
infrastructure as code. PostgreSQL, Redis, and any model-serving containers are
provisioned and run by the existing platform tooling maintained separately. Both
repositories connect to those services through configuration and assume nothing about
how they are hosted.

---

## Repository layout

This repository is the API, the ingestion worker, the shared contract and the
documentation. The web client is a separate repository, `askau-frontend`, owned by a
different team (ADR-0017).

```
ask_au/
├── Makefile            delegates to components; never reaches inside one
├── contracts/          openapi.json — generated here, consumed by askau-frontend
├── api/                Python · FastAPI · API + ingestion worker
└── docs/               requirements, architecture, decision records
```

**One component, and the delegation stays anyway.** The root `Makefile` only ever calls
`make -C <component>`, and `api` builds, tests and deploys from its own directory with no
reference to the root. That is what makes the ingestion worker separating out — or a
second consumer arriving — an addition rather than a restructure. If
`make -C api check` stops working standalone, the component is broken regardless of what
the root reports.

**The contract carries what a compiler cannot.** With the client in another repository,
changing a response shape does not break a build anywhere. Three mechanisms stand in, and
unlike the pinned-ref workflow ADR-0013 imagined, all three are built:

| Mechanism | What it catches |
|---|---|
| `contracts/openapi.json`, committed | An interface change appears in the diff of the merge request that caused it |
| `make contract-check` | The API changed and the contract did not — fails the build |
| `api/tests/contract/` | Our payloads against the client's *own* TypeScript types, read from its checkout rather than a snapshot. Also pins the places the two models deliberately differ, so a difference cannot quietly become a defect |

The window between an API merge and a client merge is real and these narrow it rather than
closing it. ADR-0017 states why that trade was taken.

---

## `contracts/`

`openapi.json`, generated by the API and consumed by `askau-frontend`. Owned by neither.

Committed rather than generated on demand, because a generated artefact nobody can see
cannot be reviewed: in the tree, an interface change appears in the diff of the merge
request that caused it, where a reviewer who knows the client can object before it ships.
`make contract-check` fails when the API has changed and the contract has not.

## `api/`

Ports & adapters (hexagonal). The layering is not stylistic — tenet T4 (everything
replaceable) and the security review both require that `rag/` and `domain/` cannot
reach a vendor SDK, and that is only enforceable when the layers are directories.

```
domain/      pure types, zero I/O, zero framework imports
rag/         orchestration — depends only on ports
retrieval/   port + adapters  ─┐
llm/         port + adapters   ├─ the only places vendor SDKs may appear
ingestion/   port + adapters  ─┘
api/         HTTP edge — thin; translates HTTP ⇄ domain, holds no logic
db/          persistence
core/        cross-cutting (config, identity, authz, errors, cache)
```

Import direction is one-way: `api → rag → {ports} → domain`. Nothing points back.

**There is no worker process, and the absence is now deliberate.** An earlier version of
this page described `workers/main.py`, a queue consumer and a `schedules/` package. The
directories existed and were empty, and `make worker` named a module that did not import
— scaffolding that reads as a feature and fails the first time anyone tries it.

Periodic work runs on demand instead, through scripts an operator invokes: `make ingest`
for one ingestion pass, `make reconcile-acls` for one ACL sweep. ADR-0025 left scheduling
to whoever operates the deployment, which already has a scheduler; a second one inside the
application would be a worse version of it. The scripts are the seam, and what runs them
on a timer is the deployment's business.

If a queue consumer is ever wanted, it belongs **inside this package** rather than in its
own repository — it would share the domain model, the ports, the ingestion pipeline and
the settings, and splitting it out would mean either duplicating that code or publishing
an internal library. One package, two entrypoints: a *deployment* distinction.

## The web client

Not in this repository. `askau-frontend` — Next.js 16, NextAuth v5 with Microsoft Entra,
next-intl across four locales (en, fr, ar with RTL, pt), Tailwind + Radix.

What matters here is only the boundary:

- It reaches us at `NEXT_PUBLIC_API_BASE_URL` + a relative path, so the API is served at
  `/api/v1` and its base is set to match.
- It authenticates over a **server-side proxy it owns**: NextAuth holds the Entra access
  token, a route handler attaches `Authorization: Bearer`, and no token reaches the
  browser. Our `EntraTokenVerifier` validates it unchanged. The backend deliberately does
  *not* read its session cookie — that would couple our auth boundary to a frontend
  library's private format and an unpinned cookie name.
- Its hand-written types in `types/` and `features/chat/types/` are the shapes this API
  serves, and `api/tests/contract/` asserts that against the files themselves.

Two properties of that client shape our payloads and are worth knowing before changing a
response:

**Its answer rendering has no default branch.** `features/chat/components/ai-message.tsx`
is a chain of `state === "x" &&` blocks with nothing unconditional, so a state it does not
recognise renders an *empty message* — not a fallback, not the answer text. Our eight
answer states are therefore mapped onto its five in `api/mappers.py`, with the unmapped
value carried alongside as `answerState`.

**Its role check compares by index.** `lib/auth/permissions.ts` treats roles as an ordered
hierarchy, so a role string it does not declare ranks below `user`. `/api/v1/users/me`
emits only `user` / `admin`, while the backend keeps enforcing the four granular roles
§6.4 separates.

## 3. The contract between components

Same repository, so a spanning change is one diff and one review — but the API and its
client are still built from different toolchains, and TypeScript does not typecheck
Python. Two mechanisms, not the four ADR-0013 needed:

**1. The API generates and commits the contract.**
`make contract` runs `python -m askau.scripts.export_openapi` and writes
`contracts/openapi.json` at the repository root. Never hand-maintained, so it cannot
drift from the code. `make contract-check` regenerates and fails on any diff.

**2. Our payloads are checked against the client's own types.**
`api/tests/contract/` reads the TypeScript interfaces out of the `askau-frontend` checkout
and asserts every field they declare is present in what we send. Reading their files rather
than a copied snapshot is the point — a snapshot agrees with itself forever, whereas this
notices when *they* change something. It skips cleanly when the frontend is not checked
out, the same way the database tests skip without a database.

Their client does not yet generate types from the contract; its types are hand-written and
nothing calls the API at all. Until that changes, this check is the only thing standing
between a response-shape change and a broken screen.

There is no version pinning between them, deliberately: pinning existed to decouple two
release timelines that no longer need decoupling, and it only ever hid drift behind a
green build until the day the pin was bumped.

**Deferred, not dropped:** the breaking-change changelog (`contracts/CHANGELOG.md`) and
consumer-driven contract tests remain the right mechanisms for the Phase 2 integration
layer, where consumers genuinely sit outside this repository and cannot be typechecked
against it. They are not load-bearing for the web client and are not built yet.

### Local development

Every component expects Postgres and Redis to be running under the external platform
tooling, reached through `.env`:

```
api/.env → ASKAU_DATABASE_URL, ASKAU_REDIS_URL
web/.env      → ASKAU_API_BASE_URL
```

No component starts, stops, or defines those services. With `ASKAU_LLM_PROVIDER=echo`
and `ASKAU_EMBEDDING_PROVIDER=hash`, the API runs the full pipeline deterministically
with no cloud credentials — which is what makes the frontend developable and CI runnable
without a model endpoint.

## 4. Enforced boundaries

Rules that make the architecture non-optional rather than aspirational.

**`api`** — `import-linter` contracts, run as a CI check:

| Contract | Rule |
|---|---|
| `domain-is-pure` | `askau.domain` imports nothing from `askau.*` |
| `rag-uses-ports-only` | `askau.rag` may not import `*.adapters` or any vendor SDK |
| `no-sdk-outside-adapters` | `openai`, `azure.*`, raw `httpx` importable only under `*/adapters/` |

**`web`** — ESLint rules, run by `npm run lint`:

| Rule | Purpose |
|---|---|
| No `fetch` outside `lib/api/` | All API access goes through the typed client |
| No hand-written response types | Only `lib/api/generated/` |
| No hardcoded user-facing strings | i18n readiness |
| No secrets or tokens in client components | The access token stays server-side |

Code that reaches for a vendor SDK from the orchestration layer, or writes a raw `fetch`
against an endpoint whose shape it invented, fails `make check`. That is the only way
these boundaries survive contact with delivery pressure — and it works today, before any
pipeline exists.

## 5. Development workflow — and why CI is deferred

CI is not being set up yet. The pipeline is designed (`14-ci-and-code-quality.md`) but
not built, because a pipeline is worth little until there is an application for it to
verify.

**The deferral only works because of one rule: every check CI will eventually run must
be a command a developer can run today.** CI, when it lands, is a thin wrapper that
calls those same commands and nothing else. That keeps two properties that are otherwise
lost:

- A check that only exists in CI cannot be run locally, so it gets discovered as a
  surprise failure after push rather than before commit.
- A pipeline written against commands that already work is an afternoon of YAML. A
  pipeline written from scratch against an unfamiliar codebase is a week, and it tends to
  encode logic that then exists nowhere else.

### `api` — the Makefile is the developer interface

```
make setup            install deps, install pre-commit hooks
make migrate          alembic upgrade head
make seed             load the synthetic corpus and test identities
make run              uvicorn with reload
make worker           run the ingestion consumer

make test             full suite
make test-unit        no database needed
make test-security    the TC-SEC isolation suite
make lint             ruff check + format check + import contracts
make typecheck        mypy
make contract         regenerate contracts/openapi.json
make contract-check   regenerate and fail on drift
make eval             the RAG evaluation gate

make check            lint + typecheck + test + contract-check
```

`make check` is the whole future pipeline in one command. When CI arrives, its job
scripts are `make check` split across stages for parallelism — not a reimplementation.

### The web client

Not in this repository — see `askau-frontend`. To run the contract check against a
checkout elsewhere:

```
ASKAU_FRONTEND_PATH=/path/to/askau-frontend make -C api test
```

### Running the two together

Both repositories checked out side by side, PostgreSQL and Redis already running under
the platform tooling:

```
api/.env   ASKAU_DATABASE_URL, ASKAU_REDIS_URL
                      ASKAU_LLM_PROVIDER=echo
                      ASKAU_EMBEDDING_PROVIDER=hash
                      ASKAU_AUTH_MODE=dev

web/.env        ASKAU_API_BASE_URL=http://localhost:8080
                      ASKAU_CONTRACT_PATH=../api/contracts/openapi.json
```

Three deliberate choices make the dev loop fast and credential-free:

| Setting | Effect |
|---|---|
| `ASKAU_LLM_PROVIDER=echo` | Deterministic canned generation. The full pipeline runs — retrieval, evidence gate, citation validation — with no model endpoint and no cost |
| `ASKAU_EMBEDDING_PROVIDER=hash` | Deterministic vectors from a hash. Retrieval is exercised end to end; ranking quality is meaningless, which is fine for everything except evaluation |
| `ASKAU_AUTH_MODE=dev` | Locally-signed test tokens for the seeded identities, so permission behavior is testable without an Entra tenant |

The seeded identities matter more than they look. `make seed` creates users across
several departments with deliberately overlapping group membership, so a developer can
switch identity and *see* permission-aware retrieval change what comes back. Without
that, the system's most important property is invisible during development and only
gets verified by a test suite nobody watches.

### When CI gets added

Once the API answers a question end to end against seeded content and the interface
renders it — the Month 2 gate in `11-implementation-plan.md`. At that point there is
something worth protecting from regression, `make check` already exists and passes, and
wiring it up is mechanical.
